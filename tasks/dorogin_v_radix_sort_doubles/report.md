## 1. Введение

Моя задача — реализовать последовательную и параллельную (MPI) версии алгоритма поразрядной сортировки для вещественных чисел (`double`) с последующим простым слиянием отсортированных блоков.  
Также необходимо написать функциональные тесты, проверяющие корректность работы обеих реализаций, и тесты на производительность для сравнения SEQ и MPI вариантов.

Поразрядная сортировка позволяет эффективно сортировать числа по битам/байтам. Для вещественных чисел требуется дополнительное преобразование представления, чтобы обеспечить корректный порядок (учёт знака, порядка и мантиссы).

## 2. Постановка задачи

**Вход:** одномерный вектор вещественных чисел `std::vector<double>` произвольного размера.  
**Выход:** вектор той же длины, содержащий элементы входного вектора, отсортированные по неубыванию.

### Описание алгоритма

1. Каждое число типа `double` переводится во вспомогательное целое представление `uint64_t`, которое обеспечивает лексикографическую упорядоченность по значению:
   - положительные числа сдвигаются так, чтобы их порядок сохранялся;
   - отрицательные инвертируются так, чтобы все отрицательные оказались "меньше" положительных и порядок среди них также сохранялся.
2. К полученному массиву `uint64_t` применяется стабильная поразрядная сортировка по байтам (LSD radix sort, 8 проходов по 1 байту).
3. Упорядоченное представление `uint64_t` переводится обратно в `double`.

Краевые условия:
- пустой вектор корректно обрабатывается (алгоритм не падает, результат — пустой вектор);
- алгоритм должен корректно работать с:
  - отсортированными и обратно отсортированными последовательностями;
  - повторяющимися значениями;
  - смешанными положительными и отрицательными числами;
  - достаточно большими размерами вектора (десятки и сотни тысяч элементов и более).

## 3. Базовый алгоритм (последовательный, SEQ)

Последовательная версия реализована в классе `DoroginVRadixSortDoublesSEQ` (`seq/src/ops_seq.cpp`).

Основные шаги:
1. В `PreProcessingImpl` входной вектор копируется во внутренний буфер `data_`.
2. В `RunImpl` выполняется поразрядная сортировка:
   - преобразование `double -> uint64_t` с учётом знака;
   - 8 проходов по байтам от младшего к старшему с учётом стабильности;
   - обратное преобразование `uint64_t -> double`.
3. В `PostProcessingImpl` отсортированный вектор записывается в `GetOutput()`.

Упрощённый фрагмент кода:

```cpp
uint64_t ToSortable(double x) {
  uint64_t u;
  std::memcpy(&u, &x, sizeof(double));
  return (u & (1ULL << 63)) ? ~u : (u ^ (1ULL << 63));
}

double FromSortable(uint64_t u) {
  u = (u & (1ULL << 63)) ? (u ^ (1ULL << 63)) : ~u;
  double x;
  std::memcpy(&x, &u, sizeof(double));
  return x;
}

void RadixSort(std::vector<double>& vec) {
  const std::size_t n = vec.size();
  std::vector<uint64_t> a(n), tmp(n);

  for (std::size_t i = 0; i < n; ++i) {
    a[i] = ToSortable(vec[i]);
  }

  for (int byte = 0; byte < 8; ++byte) {
    std::size_t count[256]{};

    for (auto v : a) {
      ++count[(v >> (byte * 8)) & 0xFF];
    }

    std::size_t pos[256]{};
    for (int i = 1; i < 256; ++i) {
      pos[i] = pos[i - 1] + count[i - 1];
    }

    for (auto v : a) {
      tmp[pos[(v >> (byte * 8)) & 0xFF]++] = v;
    }

    a.swap(tmp);
  }

  for (std::size_t i = 0; i < n; ++i) {
    vec[i] = FromSortable(a[i]);
  }
}
```

Корректность последовательного варианта проверяется через сравнение результата с эталонным вектором, отсортированным с помощью стандартного `std::sort`.

## 4. Схема распараллеливания (MPI)

Параллельная версия реализована в классе `DoroginVRadixSortDoublesMPI` (`mpi/src/ops_mpi.cpp`).

Принцип работы:
1. На процессе с `rank 0` весь входной вектор берётся из `GetInput()`, его размер обозначим `n`.
2. Размер делится на число процессов `size`; формируются массивы:
   - `counts[i]` — сколько элементов обрабатывает процесс `i`;
   - `displs[i]` — смещение блока процесса `i` во входном векторе.
3. `MPI_Scatterv` распределяет подмассивы между процессами:
   - каждый процесс получает свой локальный блок `local`.
4. Каждый процесс выполняет **локальную поразрядную сортировку** над своим блоком, вызывая общую функцию `RadixSort(local)`.
5. `MPI_Gatherv` собирает отсортированные блоки на `rank 0` в вектор `gathered`.
6. На `rank 0` выполняется **простое последовательное слияние** отсортированных отрезков с помощью `std::inplace_merge`.
7. Итоговый отсортированный вектор рассылается всем процессам через `MPI_Bcast`, и каждый процесс записывает результат в `GetOutput()`. Это важно для корректной работы perf-тестов, которые проверяют результат на всех рангах.

Псевдокод:

```cpp
// распределение
MPI_Scatterv(input.data(), counts.data(), displs.data(), MPI_DOUBLE,
             local.data(), counts[rank], MPI_DOUBLE,
             0, MPI_COMM_WORLD);

// локальная сортировка
RadixSort(local);

// сбор локально отсортированных блоков
MPI_Gatherv(local.data(), counts[rank], MPI_DOUBLE,
            gathered.data(), counts.data(), displs.data(), MPI_DOUBLE,
            0, MPI_COMM_WORLD);

// на rank 0: последовательное слияние
for (int i = 1; i < size; ++i) {
  std::inplace_merge(gathered.begin(),
                     gathered.begin() + displs[i],
                     gathered.begin() + displs[i] + counts[i]);
}

// рассылка результата всем процессам
MPI_Bcast(result.data(), n, MPI_DOUBLE, 0, MPI_COMM_WORLD);
GetOutput() = result;
```

Каждый процесс работает параллельно только со своей частью массива, а глобальное упорядочение достигается за счёт простого последовательного слияния на корневом процессе.

## 7. Результаты и обсуждение

### 7.1 Корректность

Функциональные тесты на базе `BaseRunFuncTests` выполняют для каждого набора входных данных следующее:
- формируют эталонный результат `expected_` с помощью `std::sort`;
- запускают SEQ и MPI задачи;
- сравнивают `output_data` с `expected_` на точное совпадение.

Все 14 функциональных тестов прошли успешно как для SEQ, так и для MPI реализации:
- пустые векторы;
- одиночные элементы;
- уже отсортированные и обратно отсортированные последовательности;
- наличие дубликатов;
- смешанные положительные и отрицательные значения.

### 7.2 Производительность

Время измерялось с помощью инфраструктуры `BaseRunPerfTests` (режим `kPipeline`) для различных чисел процессов MPI (`mpiexec -n {1, 2, 4, 8}`).  
В качестве базового времени используется последовательная реализация (SEQ) при одном процессе.

Из логов запуска:
- SEQ, `n=1`: `dorogin_v_radix_sort_doubles_seq_enabled:pipeline:0.0135856800`
- MPI, `n=1`: `dorogin_v_radix_sort_doubles_mpi_enabled:pipeline:0.0146191400`
- MPI, `n=2`: `dorogin_v_radix_sort_doubles_mpi_enabled:pipeline:0.0118235600`
- MPI, `n=4`: `dorogin_v_radix_sort_doubles_mpi_enabled:pipeline:0.0170379600`
- MPI, `n=8`: `dorogin_v_radix_sort_doubles_mpi_enabled:pipeline:0.0193543200`

Комментарии:
- При 1 процессе MPI‑реализация немного медленнее SEQ из‑за дополнительных накладных расходов MPI‑инициализации и коммуникаций.
- При 2 процессах наблюдается небольшое ускорение относительно базового SEQ (speedup ≈ 1.15), однако эффективность далека от идеальной.
- При 4 и 8 процессах ускорение падает, так как:
  - объём вычислений на процесс становится относительно небольшим;
  - растут накладные расходы на `MPI_Scatterv`, `MPI_Gatherv`, `MPI_Bcast` и слияние на процессе 0;
  - этап простого последовательного слияния на процессе 0 становится узким местом.

В целом для выбранного размера данных и схемы "простого слияния" сильного масштабирования по числу процессов добиться не удаётся, но цель лабораторной — продемонстрировать корректную параллельную схему, а не максимальное ускорение.
